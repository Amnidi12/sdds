# Troubleshooting

## Local setup issues

**`docker compose up` fails on the `api` service with a database connection error**
The `api` service depends on `postgres` being *healthy*, not just started — Postgres can take a few seconds to accept connections on first boot. Compose's `depends_on: condition: service_healthy` should handle this, but if it doesn't, run `docker compose up postgres redis` first, wait for both healthchecks to pass, then `docker compose up api web`.

**`alembic upgrade head` fails with "relation already exists"**
You likely ran migrations against a database that already has tables from a previous manual `create_all()` call. Drop and recreate the database, or `alembic stamp head` if the schema is already correct.

**Login works but subsequent requests return 401**
Check that your frontend is calling the API with `credentials: "include"` (the provided `lib/api.ts` already does this) and that `CORS_ORIGINS` on the backend includes your exact frontend origin — CORS with credentials does not work with a wildcard `*` origin.

**Cookies aren't being set at all**
If you changed `COOKIE_DOMAIN` in `.env`, make sure it matches the actual host you're accessing the app from. Setting `COOKIE_DOMAIN=localhost` while accessing via `127.0.0.1` (or vice versa) will silently prevent the cookie from being stored — this is standard browser behavior, not a bug. The default config leaves this unset for exactly this reason.

**`pip install` fails on `argon2-cffi` or `asyncpg`**
These have C extensions. On Debian/Ubuntu, `apt install build-essential libpq-dev python3-dev` first. On the Docker path this is already handled in the Dockerfile.

## CI issues

**Backend CI fails on `ruff check` for unused imports in a file you didn't touch**
Run `ruff check app/ --select=F,E9 --fix` locally and commit the result — the CI config intentionally only fails on real errors (`F`, `E9`), not style (`E501` is ignored), so a failure here is a genuine unused-import/undefined-name issue.

## Known gaps in this build (read before claiming "production ready")

This was built iteratively in a conversational session with real, tested code at every step — but the full 55-section original specification is genuinely months of work. Here's the honest state as of this build:

**Implemented, tested, working:**
- Auth (register/login/logout/refresh/password reset/email verification), RBAC, org-tenant isolation
- Donation lifecycle with enforced state machine
- Warehouse/inventory with transactional stock locking
- Pickup task workflow (volunteer state machine)
- Beneficiary records + requests (privacy-scoped)
- Distribution workflow that closes the loop back to donor-visible "completed"
- Public tracking endpoint with PII exclusion
- 13 passing backend tests covering the above
- Donor-facing frontend (landing, register, login, dashboard, create donation)
- Docker Compose, Dockerfiles, CI workflows, Alembic migration, seed script

**Modeled in the database but not yet exposed via API/UI:**
- File uploads (donation photos, delivery proof photos) — `donation_media` and `delivery_proofs.photo_storage_key` columns exist; the actual upload endpoint with MIME/size validation does not
- QR code image generation (the tracking URL format is defined in `app/donations/tracking.py::build_qr_payload`; rendering it as an actual QR image via the `qrcode` package listed in requirements.txt is not yet wired to an endpoint)
- Notifications (the `notifications` table and model exist; nothing currently writes to it)
- Reports/CSV export
- Admin panel (organization/user management)

**Not started:**
- NGO Admin, Volunteer, and Admin dashboard UI (the APIs they'd call are built and tested; the React pages are not)
- Google OAuth
- Playwright e2e tests
- Frontend unit tests (Vitest)
- Dependency vulnerability scanning in CI

**Environment limitation encountered during this build:**
PostgreSQL could not be installed in the sandbox this was built in (package mirror didn't have it available), so:
- The initial Alembic migration was hand-written to mirror the models rather than autogenerated — verify it with `alembic check` against real Postgres before trusting it in production (see `docs/database.md`)
- Docker images were never actually built/run in this environment — the Dockerfiles follow standard, well-tested patterns (multi-stage, non-root user, healthcheck) but haven't been build-verified here. Run `docker compose up --build` yourself as the first real test.

If you're picking this project up to finish it, the highest-value next steps in order are: (1) build the NGO Admin dashboard since all its APIs already exist and are tested, (2) wire the file upload endpoint since two DB columns are already waiting for it, (3) add the notification-writing calls at each key transition point (approval, pickup assignment, distribution completion) since the table and the trigger points are both already there.
